# 录完屏，为什么还要从头写一遍教程？我做了「录见」

最近我在做一个东西，叫「录见」。

它想解决一件很具体的事：

**把一段软件操作录屏，整理成一份可以继续编辑、复核和交付的图文教程。**

很多教程并不是不会写，而是写起来太重复。

操作已经在屏幕上做过一次，之后还要重新回放视频、暂停、截图、排序、补文案、检查隐私，再整理成可以发布的格式。

我想试着把这条链路缩短。

这段时间，我先做了两个可以独立验证的部分：本地候选画面提取，以及教程的编辑、复核和导出。

![录见 V0.1 产品演示高光](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/%E5%BD%95%E8%A7%81-V0.1-%E6%BC%94%E7%A4%BA%E9%AB%98%E5%85%89.gif)

*同一个自有案例：本地筛选候选画面，Web 工作台负责编辑、复核和导出。*

先看一次真实运行。

我用一段自有产品录屏做了本地验证：

- 17.83 秒录屏；
- 最终保留 7 张候选画面；
- 验收记录中的一次运行耗时为 2.06 秒。

![17.83 秒自有录屏提取出的 7 张候选画面](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/cli-contact-sheet.jpg)

*同一段自有录屏经本地命令行工具（CLI）实际运行后得到的 7 张候选画面，时间点依次为 0.50、3.00、4.50、6.75、9.25、11.00 和 13.50 秒。*

目前，这两部分已经可以运行；负责选图、合并和生成步骤文案的语义层还没有接上。这就是录见 V0.1：一套正在补齐中间桥接的工程原型。

## 一、项目整体说明

### 1.1 产品全景：录见到底要做什么

录见面向的是一类反复出现的工作：

- 产品经理录完功能演示，要整理操作说明；
- 培训老师录完软件流程，要制作课件和学员手册；
- 客服或实施人员处理完问题，要沉淀标准操作教程；
- 团队完成一次内部流程，要把经验变成可以复用的文档。

它最终希望形成这样的闭环：

~~~text
软件操作录屏
  → 找到值得保留的关键画面
  → 理解操作与业务含义
  → 生成可编辑的教程初稿
  → 人工复核文字与截图
  → 导出 Markdown、公众号富文本或独立图文包
~~~

为了避免一开始就把所有问题混在一起，我把产品拆成了三部分。

第一部分，是本地媒体处理。

它只负责读取视频、寻找画面变化、保留候选截图和时间信息，不理解业务语义。

第二部分，是语义转换。

它需要判断哪些候选属于同一个操作、哪些画面应该删除、每一步在做什么，以及如何生成步骤文案。

第三部分，是教程交付。

它负责编辑、排序、隐藏步骤、复核修改、检查截图隐私，并把结果导出成可以继续使用的文件。

这三部分分别处理画面召回、语义决策和交付复核，不把所有问题塞给一次模型调用。

![录见 V0.1 产品全景架构](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/reference-standard/01-product-architecture.png)

*录见产品全景：从真实使用场景和录屏输入出发，最终交付可编辑教程、公众号内容或独立图文包。*

### 1.2 端到端流程：已完成和未完成必须放在一张图里

如果只看产品界面，很容易误以为用户选择视频后，系统已经自动生成了 6 步教程。

实际代码不是这样工作的。

当前真实流程分成两条。

第一条是本地命令行工具（CLI）：

~~~text
真实录屏
  → ffprobe 读取媒体信息
  → 场景检测 + 周期灰度采样
  → 聚类、覆盖补帧、相邻画面去重
  → 7 张候选截图
  → candidates.json
  → review.html
~~~

第二条是 Web：

~~~text
选择 MOV / MP4
  → 只校验文件名和类型
  → 回放自有案例处理状态
  → 载入 6 步预置 TutorialStep[]
  → 编辑、复核、隐私检查
  → 导出教程
~~~

两条流程之间目前缺的是：

~~~text
candidates[]
  → 选择有效画面
  → 合并连续动作
  → 理解业务语义
  → 生成标题与说明
  → TutorialStep[]
~~~

![录见从录屏到教程交付的端到端流程](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/reference-standard/02-end-to-end-flow.png)

*当前端到端流程图：实线表示已经实现，虚线表示尚未接通。*

这个拆分很重要。

变化检测只能证明“画面变了”，不能证明“用户完成了一个值得写进教程的动作”。

例如，本次 CLI 候选中，9.25 秒和 11.00 秒都保留了任务详情中的相近过程状态，13.50 秒才回到完成后的看板。

对像素算法来说，它们都是值得检查的变化；对教程来说，还要判断前两张是否应该合并、哪张最能说明过程、最终结果应该由哪张承担。

这正是语义层要解决的问题。

### 1.3 技术组件与分层：每个模块只解决一种不确定性

录见 V0.1 的技术栈并不复杂，但每一层的职责被刻意分开了。

#### 本地媒体处理层

- Python 3.10 或更高版本；
- 只使用 Python 标准库；
- 调用本机 ffmpeg 与 ffprobe；
- 读取呈现时间戳（PTS）、场景变化和灰度画面；
- 输出 JSON、JPEG、离线评审页和待使用提示词；
- 不调用模型 API，不发起网络请求。

#### 语义转换层

- 当前尚未实现；
- 目标输入是经过人工隐私检查的候选画面与候选元数据；
- 目标输出是可以进入 Web 的教程步骤结构；
- 是否采用 OCR、多模态模型或规则组合，仍需通过真实样本评估后决定。

#### Web 教程交付层

- React 19 + TypeScript；
- 当前使用 6 步自有预置数据；
- 草稿保存在当前浏览器的 localStorage；
- ZIP 由浏览器本地生成；
- 支持 Markdown、公众号富文本和独立图文包三种交付方式；
- 没有接收 CLI 结果的后端接口。

![录见 V0.1 技术组件依赖图](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/reference-standard/03-technical-layers.png)

*技术组件图：CLI 模块、运行产物、待实现的转换器，以及 Web 状态机和导出模块之间的依赖关系。*

**我的判断是：录屏转教程并不是一个“大模型写作”问题，而是媒体召回、语义决策和人工交付三个不同问题的组合。**

把三件事塞进一次模型调用，演示可能很快，但很难知道漏了哪一步、为什么选了这张图，也很难在发布前做可靠复核。

**如果你更关心产品效果，可以直接跳到第二部分；下面两节留给想看数据结构和实现细节的读者。**

CLI 和 Web 已经放进同一个代码仓库，方便读者分别运行、核验和继续开发。

CLI 每次运行会生成一套独立结果包：

~~~text
result/
├── metadata.json
├── candidates.json
├── review.html
├── model_prompt.md
└── screenshots/
    ├── C001_000000.500s.jpg
    ├── C002_000003.000s.jpg
    └── ...
~~~

这里最重要的不是 JPEG，而是候选数据契约。

下面是本次真实结果中 C005 的字段摘录：

~~~json
{
  "id": "C005",
  "timestamp": {
    "requested_seconds": 9.25,
    "actual_seconds": null
  },
  "screenshot": {
    "relative_path": "screenshots/C005_000009.250s.jpg",
    "privacy_status": "unreviewed"
  },
  "detection": {
    "sources": ["coverage"]
  },
  "review": {
    "status": "pending",
    "keep": null
  }
}
~~~

这里专门把“截图请求时间”和“实际解码时间”分开。

当前程序读取 ffmpeg 输出的 pts_time，并把 9.25 秒作为截图请求目标；但它还没有独立测量最终解码帧的真实 PTS，所以 actual_seconds 明确保留为 null。

我不希望为了让数据看起来完整，就把请求时间复制一份冒充测量结果。

Web 当前使用的步骤结构是：

~~~typescript
type TutorialStep = {
  id: number;
  time: string;
  title: string;
  body: string;
  image: string;
  imageHeight: number;
  included: boolean;
  confidence: number;
};
~~~

当前 6 步 TutorialStep 来自代码中的 INITIAL_STEPS 预置数组，其中的 confidence 也是演示数据，不是模型推理置信度。

候选数据与教程步骤还不是同一种结构。

候选侧保留 C005、截图请求时间（以 PTS/pts_time 为基准）、检测来源、截图摘要和人工评审状态；Web 侧更关心标题、正文、图片、顺序和是否纳入。

因此，中间桥接不能只做一次字段改名。

它必须保留“一个教程步骤来自哪些候选画面”的来源关系，否则编辑完成后，就无法再追溯步骤文案对应了哪一段视频。

### 1.5 核心代码

以下 Python 代码均来自本地 CLI 的 `cli/video_guide.py`；Web 状态与门禁代码来自 `app/page.tsx`，导出代码来自 `lib/tutorial-export.ts`。这里只保留决定行为的主体逻辑，完整上下文以对应工程文件为准。

#### 1.5.1 两路信号先解决召回

CLI 第一条信号以 8 fps、640 px 分析 scene score，用来捕捉明显页面切换。

第二条信号以 1 fps、160 px 读取灰度帧，用 MAD，也就是平均绝对差，寻找周期采样中的局部峰值。

周期阈值不是一个写死的固定值：

~~~python
differences = [
    mean_absolute_difference(
        samples[index - 1].pixels,
        samples[index].pixels,
    )
    for index in range(1, len(samples))
]

baseline = statistics.median(differences)
spread = statistics.median(
    abs(value - baseline) for value in differences
)
threshold = max(
    config.periodic_mad_floor,
    baseline + config.periodic_noise_multiplier * spread,
)
~~~

程序先计算相邻采样差异的中位数，再用中位绝对偏差估算波动。

这样，相对安静的录屏和变化频繁的录屏，不必共用完全相同的判断线。

#### 1.5.2 信号不足时，主动补一层低频覆盖

真实录屏很快暴露了一个问题：渐进加载、小弹窗和短菜单不一定产生明显场景切点。

如果相邻候选之间长时间没有信号，程序会按设定间隔补充低频覆盖候选，直到下一个已有候选点。

它不是把每个 1 fps 采样都变成输出，而是在信号稀疏区间保留一层召回兜底。

本次 7 张候选使用了 2.5 秒覆盖补帧间隔；CLI 默认值仍是 5 秒。

#### 1.5.3 去重不能只看全屏平均值

短菜单可能只占画面的一小块。

全屏 MAD 很低，不代表局部区域没有重要变化。

因此，去重同时计算全局 MAD 和 4 × 4 区域中的最大局部 MAD，只有两者都低于阈值时才丢弃：

~~~python
if (
    difference < config.dedup_mad_threshold
    and tile_difference < config.dedup_tile_mad_threshold
):
    discarded.append(
        {
            "requested_seconds": round(
                proposal.requested_timestamp,
                6,
            ),
            "reason": "adjacent_visual_duplicate",
        }
    )
    continue
~~~

本次自有实录中，被丢弃的 3 个相邻候选全局 MAD 分别是 0.0029、0.0516 和 0.0516；对应局部 MAD 也低于阈值。

算法因此把它们判定为相邻视觉重复。

但“视觉重复”不等于“业务上一定无用”，最终仍要由人工结合原视频确认。

这四种机制组合起来，解决的是“先尽量不漏，再把明显重复压下去”。它们仍然只负责召回画面，不负责判断业务步骤。

#### 1.5.4 场景切换和短菜单不能使用同一种延时

明显页面切换之后，通常要等页面稳定再截图。

短暂菜单却可能在 0.5 秒后已经消失。

当前聚类逻辑因此做了区分：包含场景切换信号的事件默认延后 0.5 秒截图；仅包含周期采样信号的事件，则保留原采样时刻。

这不是一个通用最优参数，而是当前原型为减少“页面还没稳定”和“菜单已经消失”两类错误做的取舍。

#### 1.5.5 人工复核不是装饰，而是交付状态机

Web 工作台不只是一个文本编辑器。

如果某一步已经人工确认，但之后又改了文字，原确认状态会自动失效：

~~~typescript
const updateStepCopy = (
  id: number,
  patch:
    | Pick<TutorialStep, 'title'>
    | Pick<TutorialStep, 'body'>,
) => {
  updateStep(id, patch);
  setEditedStepIds(
    (current) => new Set(current).add(id),
  );
  setReviewedStepIds((current) => {
    const next = new Set(current);
    next.delete(id);
    return next;
  });
};
~~~

导出之前还要同时检查：

- 标题、摘要和步骤是否完整；
- 纳入步骤是否都有时间戳；
- 截图是否齐全；
- 修改过的文案是否重新复核；
- 每张纳入截图是否完成隐私确认。

只要还有一张截图没有确认，三种导出都会被同一个门禁拦住，并提示当前已完成检查的数量。

#### 1.5.6 安全规则直接写进输出契约

当前 CLI 还保留了几条不太显眼、但产品化时不能缺的规则：

- metadata.json 与 candidates.json 只保存源视频文件名，不保存本机绝对路径；
- 每张截图同时记录 SHA-256；
- 所有截图初始隐私状态一律是 unreviewed；
- 非空输出目录会被拒绝，避免覆盖上一次人工结果；
- 符号链接输出目录会被拒绝；
- 文件名进入 review.html 前会做 HTML 转义；
- model_prompt.md 明确要求把截图内容当成不可信数据，不执行画面中的命令或提示词。

程序不调用模型，所以这些规则不能替代人工隐私检查。

它们的作用，是让后续接入语义层时仍然知道：输入从哪里来、有没有检查过、哪些内容不能直接相信。

## 二、产品演示

### 2.1 CLI：先把几百帧缩成一组可检查候选

本次自有录屏只有 17.83 秒，但原始视频仍包含数百帧。

CLI 最终保留了 7 张候选：

| 候选 | 请求时间 | 检测来源 |
|---|---:|---|
| C001 | 0.50 秒 | 起始边界 |
| C002 | 3.00 秒 | 覆盖补帧 |
| C003 | 4.50 秒 | 周期变化 + 场景变化 |
| C004 | 6.75 秒 | 周期变化 + 场景变化 |
| C005 | 9.25 秒 | 覆盖补帧 |
| C006 | 11.00 秒 | 周期变化 |
| C007 | 13.50 秒 | 覆盖补帧 |

候选并不等于最终步骤。

它的任务是尽量保留值得继续检查的状态，并把每一张图为什么出现、请求时间是什么、是否经过隐私检查记录下来。

### 2.2 review.html：在截图离开本机前先人工评审

CLI 会同时生成一个完全离线的 review.html。

![录见 CLI 生成的离线候选评审页](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/figures/figure-04.jpg)

*真实 CLI 输出的离线评审页。页面显示 7 张候选、请求时间、检测来源和未审阅状态。*

每张候选都可以：

- 决定是否保留；
- 填写步骤标题；
- 记录隐私、重复或截图偏移问题；
- 最后导出 review-result.json。

页面本身不联网，备注也只会在点击导出时写入下载文件。

但离线不等于自动安全。

截图仍可能包含账号、姓名、浏览器标签、文件名、通知或密钥。任何截图在发布或交给外部模型前，都必须逐张检查。

### 2.3 Web 首页：选择文件不等于上传和处理

Web Demo 支持选择 MOV 或 MP4。

当前 acceptFile 逻辑只检查 MIME 类型或扩展名，然后把文件名写入状态。

后续看到的处理进度，不是浏览器在分析这个文件。

### 2.4 处理页：把真实候选和教程工作台放进同一个演示

处理页展示的 4 个场景信号、6 个周期信号和 7 张候选，来自真实 CLI 验证。

随后载入的 6 步教程，是为了验证工作台交互而写入代码的预置结构。

页面中的进度是演示状态，不是实时任务进度。

### 2.5 教程工作台：生成之后，还要解决“怎样交付”

进入工作台后，可以：

- 修改文章标题和摘要；
- 修改步骤标题与说明；
- 调整步骤顺序；
- 隐藏不纳入成稿的步骤；
- 在编辑视图与预览视图之间切换；
- 保存当前浏览器草稿；
- 标记文字与画面已核对；
- 逐张确认截图隐私；
- 导出三种结果。

*录见 Web 教程工作台：左侧步骤，中间编辑与预览，右侧交付检查。*

### 2.6 修改、复核和隐私检查形成同一个门禁

![录见文案修改与重新复核](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/reference-standard/05-product-demo-review.png)

*同一份教程的连续状态：文案一旦被修改，原复核立即失效，必须再次完成人工核对。*

这里最重要的不是多一个勾选框，而是状态之间有依赖关系。

文字发生变化，原复核失效；步骤被隐藏，隐私检查只计算仍纳入的步骤；任何一项不满足，交付被阻止。

### 2.7 三种导出共用同一份数据

Web 当前支持：

1. 复制 Markdown；
2. 复制公众号富文本；
3. 下载独立 ZIP 图文包。

ZIP 在浏览器本地生成，目录如下：

~~~text
教程标题/
├── 教程.md
├── 公众号预览.html
├── 使用说明.txt
└── images/
    ├── step-01.jpg
    ├── step-02.jpg
    └── ...
~~~

如果浏览器拒绝写入富文本剪贴板，程序会自动回退为 Markdown。

![录见完成全部检查后的交付结果](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/reference-standard/06-product-demo-delivery.png)

*完成五项交付检查后，导出门禁解除；实测成功下载独立 ZIP 图文包，同一份数据也可生成 Markdown 和公众号富文本。*

## 四、当前边界

写到这里，可以把录见 V0.1 能做和不能做的事说得更准确一些。

### 已经完成

1. 在本机离线读取录屏，召回、聚类、补帧并去重候选画面；
2. 输出高分辨率截图、候选 JSON、媒体元数据和离线评审页；
3. 在 Web 中编辑预置教程，管理文案复核和截图隐私确认；
4. 导出 Markdown、公众号富文本和独立 ZIP 图文包；
5. 使用自有录屏、自有任务板和自动化测试完成公开验证。

### 尚未完成

1. Web 尚不会读取、上传或分析所选视频，CLI 候选也不会自动进入 Web；
2. 语义层尚未选择、合并候选并生成真实步骤，当前 6 步与 confidence 均为预置数据；
3. 系统还不能识别真实点击位置，也不能仅凭画面变化判断业务动作是否完成；
4. 截图隐私不会自动脱敏，资源体积、时长和分辨率也还没有产品级上限；
5. 当前版本还不是可以直接用于生产交付的端到端产品。

这也是为什么我没有把文章写成“上传录屏，AI 自动生成教程”。

现在能被真实证明的是：

**录见已经把候选画面提取和教程交付工作台分别做成了可运行原型。**

中间的语义转换，仍然是决定这个产品是否真正成立的核心。

## 五、后续规划

下一阶段不继续扩页面，也不先加团队协作、知识库发布或更多导出格式。

V0.2 只推进一条主线：

~~~text
真实录屏
  → candidates[]
  → 人工隐私检查
  → 语义选择与合并
  → 可追溯的 TutorialStep[]
  → Web 工作台
  → 复核与导出
~~~

### 第一步：先把数据桥接起来

第一步不是接模型，而是让 Web 能读入真实 CLI 结果。

需要解决：

- candidates.json 的导入；
- review-result.json 的人工保留结果；
- 候选 ID、请求 PTS、截图路径和教程步骤之间的映射；
- 一个教程步骤对应多个候选时的来源保留；
- 真实候选替换当前 INITIAL_STEPS 预置数据。

### 第二步：建立可复核的金样本

在评估任何语义模型之前，先由人工标注：

- 哪些画面属于关键操作；
- 哪些候选是重复状态；
- 哪些连续画面应该合并；
- 哪一张最适合承担步骤截图；
- 哪些信息仅凭截图无法判断。

后续不只看“模型有没有返回 JSON”，而是看：

- 关键操作有没有进入候选集；
- 连续画面有没有被正确合并；
- 截图与步骤文案是否匹配；
- 初稿还需要人工修改多少；
- 视频、时间戳、候选和最终步骤能否持续追溯。

### 第三步：再验证语义转换

只有候选质量和金样本稳定以后，才比较 OCR、规则和多模态模型的组合方式。

这部分至少要输出：

- 被选择的候选 ID；
- 被合并的候选关系；
- 步骤标题与说明；
- 不确定项；
- 缺失证据；
- 隐私警告；
- 可供人工复核的来源信息。

### 主链路成立后：再补产品化能力

等主链路成立以后，再考虑：

- 截图裁剪和局部放大；
- 自动遮挡与人工修正；
- 点击位置标注；
- 长视频任务队列、超时和磁盘配额；
- 团队审核；
- 知识库和帮助中心发布。

![录见 V0.2 路线图](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/figures/figure-09.jpg)

*V0.2 路线图：先打通候选到步骤，再讨论外围产品化能力。*

我现在最关心的，不是“模型能不能生成一篇看起来完整的教程”。

而是它能不能在不丢关键操作的前提下，把一段连续录屏变成一组可追溯、可复核、可继续编辑的步骤。

**操作已经做过一次，就不该为了写教程再做一遍。**

**你最想让「录见」替你省掉哪一步？**

产品演示、培训课件、客服 SOP，或者内部流程，都可以。
