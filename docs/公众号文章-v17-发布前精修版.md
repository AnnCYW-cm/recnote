# 录完屏，为什么还要从头写一遍教程？我做了「录见」

最近我在做一个东西，叫「录见」。

它想解决一件很具体的事：

**把一段软件操作录屏，整理成一份可以继续编辑、复核和交付的图文教程。**

很多教程并不是不会写，而是写起来太重复。

操作已经在屏幕上做过一次，之后还要重新回放视频、暂停、截图、排序、补文案、检查隐私，再整理成可以发布的格式。

我想试着把这条链路缩短。

这段时间，我先做了两个可以独立验证的部分：本地候选画面提取，以及教程的编辑、复核和导出。

![录见 V0.1 产品演示高光](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/%E5%BD%95%E8%A7%81-V0.1-%E6%BC%94%E7%A4%BA%E9%AB%98%E5%85%89.gif)

*同一个自有案例：本地筛选候选画面，Web 工作台负责编辑、复核和导出。*

先看一次真实运行。

我用一段自有产品录屏做了本地验证：

- 17.83 秒录屏；
- 最终保留 7 张候选画面；
- 本地 CLI 候选提取的一次验收运行耗时为 2.06 秒。

![17.83 秒自有录屏提取出的 7 张候选画面](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/cli-contact-sheet.jpg)

*同一段自有录屏经本地命令行工具（CLI）实际运行后得到的 7 张候选画面，时间点依次为 0.50、3.00、4.50、6.75、9.25、11.00 和 13.50 秒。*

目前，这两部分已经可以分别运行；负责选图、合并和生成步骤文案的语义层还没有接上。

这就是录见 V0.1：一套正在补齐中间桥接的工程原型。

---

## 一、录屏做完了，教程其实才刚开始

我先从一类共同任务开始验证：把软件操作过程整理成可以交付的教程。

- 产品经理录完功能演示，要整理操作说明；
- 培训老师录完软件流程，要制作课件和学员手册；
- 客服或实施人员处理完问题，要沉淀 SOP 和问题处理记录。

它们最终都要经过同一条链路：

~~~text
软件操作录屏
  → 找到值得保留的关键画面
  → 理解操作与业务含义
  → 生成可编辑的教程初稿
  → 人工复核文字与截图
  → 导出 Markdown、公众号富文本或独立图文包
~~~

![录见 V0.1 产品全景架构](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/reference-standard/01-product-architecture.png)

*录见产品全景：从真实使用场景和录屏输入出发，最终交付可编辑教程、公众号内容或独立图文包。*

## 二、我把它拆成了三层，而不是交给一次模型调用

录屏转教程看起来像一个 AI 写作问题，真正拆开以后，却至少包含三种不同的不确定性：

1. 哪些画面值得留下；
2. 哪些画面属于同一个业务步骤；
3. 生成的结果能不能被人继续编辑、复核和安全交付。

当前真实流程因此分成两段分别可运行的链路，以及中间一段尚未实现的语义桥。

~~~text
真实录屏
  → ffprobe 读取媒体信息
  → 场景检测 + 周期灰度采样
  → 聚类、覆盖补帧、相邻画面去重
  → candidates[] + review.html

candidates[]
  → 选择有效画面
  → 合并连续动作
  → 理解业务语义
  → TutorialStep[]
  （尚未实现）

预置 TutorialStep[]
  → 编辑、排序和隐藏
  → 文字复核 + 截图隐私检查
  → Markdown / 公众号富文本 / ZIP
~~~

![录见从录屏到教程交付的端到端流程](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/reference-standard/02-end-to-end-flow.png)

*当前端到端流程图：实线表示已经实现，虚线表示尚未接通。*

本地层只负责把视频缩成候选画面，不调用模型，也不发起网络请求；语义层负责把候选转换成可追溯的教程步骤，目前尚未实现；Web 层只验证编辑、复核、人工隐私确认和导出，当前使用同一自有案例的预置步骤。

![录见 V0.1 技术组件依赖图](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/reference-standard/03-technical-layers.png)

*CLI 模块、运行产物、待实现的转换器，以及 Web 状态机和导出模块之间的依赖关系。*

这里最重要的判断是：

**画面发生变化，不等于用户完成了一个值得写进教程的动作。**

例如，本次 CLI 在 9.25 秒和 11.00 秒保留了相近的过程状态，13.50 秒才回到完成后的看板。

对像素算法来说，它们都是值得检查的变化；对教程来说，还要判断前两张是否应该合并、哪张最能说明过程、哪张应该承担最终结果。

## 三、先看它现在怎么工作

### 3.1 本地筛选：从数百帧缩成 7 张候选

本次自有录屏只有 17.83 秒，但原始视频仍包含数百帧。

CLI 最终保留了 7 张候选：

| 候选 | 请求时间 | 检测来源 |
|---|---:|---|
| C001 | 0.50 秒 | 起始边界 |
| C002 | 3.00 秒 | 覆盖补帧 |
| C003 | 4.50 秒 | 周期变化 + 场景变化 |
| C004 | 6.75 秒 | 周期变化 + 场景变化 |
| C005 | 9.25 秒 | 覆盖补帧 |
| C006 | 11.00 秒 | 周期变化 |
| C007 | 13.50 秒 | 覆盖补帧 |

候选并不等于最终步骤。

它的任务是尽量保留值得继续检查的状态，记录每张图为什么出现、请求时间是什么和初始隐私状态，再通过评审页另行导出人工检查结果。

CLI 会同时生成一个完全离线的 review.html。

![录见 CLI 生成的离线候选评审页](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/figures/figure-04.jpg)

*真实 CLI 输出的离线评审页。页面显示 7 张候选、请求时间、检测来源和未审阅状态。*

在这里可以决定是否保留每张候选、填写步骤标题、记录隐私或截图偏移问题，最后导出 review-result.json。

页面本身不联网，但离线不等于自动安全。截图在发布或交给外部模型前，仍然必须逐张检查。

### 3.2 Web 回放：先验证教程工作台是否成立

Web Demo 支持选择 MOV 或 MP4，但当前只校验文件类型并记录文件名，不读取、不上传，也不分析视频字节。

![录见 Web 入口、文件选择与能力边界](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/reference-standard/04-product-demo-input.png)

*从首页到处理完成的连续状态：这里展示的是案例演示，不是实时任务进度。*

**边界说明：7 张候选来自真实 CLI；6 步教程是为了验证工作台交互而预置的数据，两者尚未自动串联。**

### 3.3 编辑与复核：文案一改，原确认就失效

进入工作台后，可以：

- 修改文章标题、摘要和步骤文案；
- 调整步骤顺序，隐藏不纳入成稿的步骤；
- 在编辑视图与预览视图之间切换；
- 保存当前浏览器草稿；
- 标记文字与画面已经核对；
- 逐张确认截图隐私。

![录见教程编辑工作台](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/reference-standard/screens/07-editor.png)

*录见 Web 教程工作台完整界面：左侧步骤，中间编辑与预览，右侧交付检查。*

如果某一步已经人工确认，但之后又改了文字，原确认状态会自动失效。

![录见文案修改与重新复核](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/reference-standard/05-product-demo-review.png)

*文案一旦被修改，原复核立即失效，必须再次完成人工核对。*

步骤被隐藏后，隐私检查只计算仍然纳入的步骤；只要有一项不满足，交付就会被阻止。

### 3.4 同一份数据，导出三种结果

Web 当前支持：

1. 复制 Markdown；
2. 复制公众号富文本；
3. 下载独立 ZIP 图文包。

ZIP 在浏览器中生成，目录如下：

~~~text

├── 公众号预览.html
├── 使用说明.txt
└── images/
    ├── step-01.jpg
    ├── step-02.jpg
    └── ...
~~~

如果浏览器拒绝写入富文本剪贴板，程序会尝试回退为 Markdown。

![录见完成全部检查后的交付结果](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/reference-standard/06-product-demo-delivery.png)

## 四、真正难的不是截几张图，而是把画面变成可信的步骤

产品界面解决的是“怎样编辑和交付”，工程上更难的问题是：怎样让每一步都能追溯到真实视频与候选画面。

接下来是实现细节；如果你更关心产品结论，可以直接跳到第五部分。

### 4.1 候选画面和教程步骤不是同一种数据

CLI 每次运行会生成一套独立结果包：

~~~text
result/
├── metadata.json
├── candidates.json
├── review.html
├── model_prompt.md
└── screenshots/
~~~

下面是本次真实结果中 C005 的字段摘录：

~~~json
{
  "id": "C005",
  "timestamp": {
    "requested_seconds": 9.25,
    "actual_seconds": null
  },
  "screenshot": {
    "relative_path": "screenshots/C005_000009.250s.jpg",
    "privacy_status": "unreviewed"
  },
  "detection": {
    "sources": ["coverage"]
  },
  "review": {
    "status": "pending",
    "keep": null
  }
}
~~~

这里专门把截图请求时间和实际解码时间分开。

程序把 9.25 秒作为截图请求目标，但还没有独立测量最终解码帧的真实 PTS，所以 actual_seconds 明确保留为 null，而不是复制请求时间冒充测量结果。

Web 当前使用的步骤结构是：

~~~typescript
type TutorialStep = {
  id: number;
  time: string;
  title: string;
  body: string;
  image: string;
  imageHeight: number;
  included: boolean;
  confidence: number;
};
~~~

当前 6 步 TutorialStep 来自 INITIAL_STEPS 预置数组，confidence 也是演示数据，不是模型推理置信度。

![候选数据与教程步骤之间的数据契约](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/figures/figure-05.jpg)

*候选数据与教程步骤的数据契约：当前结构已存在，转换器尚未实现。*

中间桥接不能只做字段改名。

它还要保留“一个教程步骤来自哪些候选画面”的关系，否则编辑完成后，就无法再追溯步骤文案对应了哪一段视频。

### 4.2 先尽量不漏，再把明显重复压下去

CLI 使用两路信号召回画面：

- 以 8 fps、640 px 分析 scene score，捕捉明显页面切换；
- 以 1 fps、160 px 读取灰度帧，用平均绝对差寻找周期采样中的局部峰值。

当相邻候选之间长时间没有信号时，程序再补一层低频覆盖。本次显式使用 2.5 秒间隔；CLI 默认值仍是 5 秒。

去重同时计算全局 MAD 和 4 × 4 区域中的最大局部 MAD。只有两者都低于阈值时，候选才会被判定为相邻视觉重复：

~~~python
if (
    difference < config.dedup_mad_threshold
    and tile_difference < config.dedup_tile_mad_threshold
):
    discarded.append(
        {
            "requested_seconds": round(
                proposal.requested_timestamp,
                6,
            ),
            "reason": "adjacent_visual_duplicate",
        }
    )
    continue
~~~

本次被丢弃的 3 个相邻候选，全局 MAD 分别是 0.0029、0.0516 和 0.0516，对应局部 MAD 也低于阈值。

但“视觉重复”不等于“业务上一定无用”，最终仍要由人工结合原视频确认。

明显页面切换和短菜单也不能使用同一种延时。当前原型会让场景事件默认延后 0.5 秒截图，而仅包含周期采样信号的事件保留原采样时刻。

这些机制只负责画面召回，不负责理解业务步骤。

### 4.3 人工复核不是一个按钮，而是交付状态机

Web 端采用 React 19 + TypeScript，草稿保存在当前浏览器的 localStorage。修改文案会让原复核失效：

~~~typescript
const updateStepCopy = (
  id: number,
  patch:
    | Pick<TutorialStep, 'title'>
    | Pick<TutorialStep, 'body'>,
) => {
  updateStep(id, patch);
  setEditedStepIds(
    (current) => new Set(current).add(id),
  );
  setReviewedStepIds((current) => {
    const next = new Set(current);
    next.delete(id);
    return next;
  });
};
~~~

导出之前，标题摘要、时间戳、截图、文字复核和截图隐私检查共用同一套门禁。

CLI 的输出契约也保留了几条产品化时不能缺的规则：

- 元数据只保存源视频文件名，不保存本机绝对路径；
- 每张截图记录 SHA-256，初始隐私状态一律是 unreviewed；
- 非空目录和符号链接目录会被拒绝，避免覆盖或写入意外位置；
- 文件名进入 review.html 前会转义，截图内容被当作不可信输入。

这些规则不能替代人工隐私检查。它们的作用，是让后续接入语义层时仍然知道输入从哪里来、有没有检查过、哪些内容不能直接相信。

## 五、它现在真实完成到了哪里

### 5.1 本次验证结果

| 验证项 | 结果 |
|---|---|
| 自有样本 | 17.833333 秒、1440 × 900、无音频 |
| CLI 结果 | 7 张候选 |
| CLI 候选提取单次验收记录 | 2.06 秒 |
| CLI 自动化测试 | 18/18 通过 |
| Web 工程检查 | npm run check 通过 |
| Web 端到端测试 | Playwright 4/4 通过 |
| CLI 网络或模型 API | 未调用 |

本次验证环境是 macOS 26.6.2、Python 3.13.2、FFmpeg / ffprobe 7.1。

输入文件 SHA-256 为 `16ebd5e9…c5186327`，完整值和验收命令记录在仓库 `cli/VALIDATION.md`。

2.06 秒只是当前设备上的一次墙钟记录，不是平均值，也不代表其他电脑、长视频或更高分辨率素材的性能。

### 5.2 已经验证与尚未接通

**已经验证：**

1. 在本机离线召回、补帧并去重候选画面；
2. 输出候选 JSON、媒体元数据、高分辨率截图和离线评审页；
3. 在 Web 中完成编辑、排序、复核、人工隐私确认门禁和三种导出；
4. 自有录屏案例、18 项 CLI 测试和 4 项 Web 端到端测试均已通过。

**尚未接通：**

1. CLI 结果还不能自动进入 Web；
2. 语义层还不能自动选择、合并候选并生成步骤；
3. 截图还不会自动脱敏，也没有生产级的时长、分辨率和资源上限。

所以，录见 V0.1 还不是一个可以直接用于生产交付的端到端产品。

它已经把“候选画面提取”和“教程交付工作台”分别做成了可运行原型；中间的语义转换，仍然是决定产品能不能真正成立的核心。

### 5.3 如何运行

点击文末“阅读原文”，可以体验录见 V0.1 Web Demo。

项目代码：`github.com/AnnCYW-cm/recnote`（复制到浏览器打开）。

Web 本地运行需要 Node.js 22.13.0 或更高版本：

~~~bash
git clone https://github.com/AnnCYW-cm/recnote.git
cd recnote
npm ci
npm run dev
~~~

候选画面 CLI 需要 Python 3.10 或更高版本，以及已经加入 PATH 的 ffmpeg 和 ffprobe，不需要 Python 第三方包。

~~~bash
python3 cli/video_guide.py \
  "/path/to/你的录屏.mov" \
  --output "/path/to/一个新目录"
~~~

为避免覆盖之前的人工结果，输出目录必须不存在或为空。

## 六、下一步，只验证中间这座桥能不能成立

V0.2 不继续扩页面，也不先增加团队协作、知识库发布和更多导出格式。

下一阶段只推进三件事。

### 第一步：让真实候选进入 Web

让 candidates.json 和人工评审结果进入工作台，并保留候选、时间戳、截图与最终步骤之间的来源关系。

### 第二步：用真实录屏建立金样本

由人工标记哪些画面应该保留、哪些应该合并、哪张最适合承担步骤截图，同时记录手工整理时间、初稿修改量和关键步骤是否遗漏。

### 第三步：比较规则、OCR 和多模态模型

不只判断模型能不能返回 JSON，而是验证：

- 关键操作有没有进入候选集；
- 连续画面合并是否合理；
- 文案与截图是否匹配；
- 初稿还需要人工修改多少；
- 视频、时间戳、候选和最终步骤能否持续追溯。

等主链路成立以后，再考虑自动遮挡、点击标注、长视频任务、团队审核和知识库发布。

![录见 V0.2 路线图](https://lujian-video-guide-demo.caiyiwenann.chatgpt.site/article/figures/figure-09.jpg)

*V0.2 路线图：先打通候选到步骤，再讨论外围产品化能力。*

我现在最关心的，不是模型能不能生成一篇看起来完整的教程。

而是它能不能在不丢关键操作的前提下，把一段连续录屏变成一组可追溯、可复核、可继续编辑的步骤。

**操作已经做过一次，就不该为了写教程再做一遍。**
